Features split into two concerns: **what you compute** and **how you serve it**.

<Diagram src="features/features-stage-subtopics.svg" />

**What to compute**

1. **Feature types**: user features (age, history, preferences), item features (category, price, embeddings), context features (time, device, location), and cross features such as "clicked this category 5 times in 7 days". Cross features are often the strongest signal.
2. **Transformations**: normalize, log-transform or bucketize numbers; one-hot encode small categoricals; use hashing or embeddings for large ones; use pretrained embeddings for text and images; impute missing values and add a missing-indicator flag.
3. **Feature selection**: measure importance (SHAP, permutation), run ablations, drop features that are redundant or too costly.

**How to serve it**

4. **Freshness**: batch (daily, e.g. lifetime spend), streaming (seconds to minutes, e.g. clicks in the last 10 minutes), or request-time (e.g. the current search query). Fresher is more predictive but costs more.
5. **Feature store**: the offline store keeps full history for training; the online store keeps latest values in a key-value store (e.g. Redis) for serving under 10 ms. Features are defined once and shared by both.
6. **Skew and leakage**: the two most common bugs in production ML. Skew means a feature is computed differently in training and serving. Leakage means a feature uses information from after the prediction time; fix it with point-in-time joins.

## Running example: card fraud detection

A card transaction arrives and you have **under 100 ms** to approve it, decline it, or ask for extra verification. The label ("was it fraud?") comes from chargebacks, which arrive **30–90 days later**.
