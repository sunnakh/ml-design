## 5.1 Latency and serving mode

### What problem it solves

The decision point (1.1) comes with a **time budget**. ShopFast's checkout API has an overall p99 target, and fraud gets **100 ms** of it. That budget decides:
- which features you can use,
- which models you can run,
- which tasks run online and which run in batch,
- and what happens when time runs out.

If you discover the budget *after* building a 2-second graph model, you rebuild. That's why latency is a framing question.

### How it works

**Step 1: pick a serving mode for each decision.**

| Mode | How it works | ShopFast use |
|---|---|---|
| **Online, synchronous** | Scored inside the request, with a strict budget | Checkout: approve / step-up / decline |
| **Online, asynchronous** | Triggered by an event; result used seconds to hours later | Pre-shipment hold and review |
| **Batch** | Precomputed on a schedule, looked up at decision time | Account risk (daily), ring scores (nightly) |
| **Streaming features** | Aggregates updated continuously, read by online models | Velocity: cards per device in the last 24h |

**Step 2: break the budget into parts.** Measure p99, not averages. Here's ShopFast's checkout path:

<Diagram src="problem-framing/checkout-fraud-latency-budget.svg" />

Reading it:
- **The common path** (no vendor call, about 85% of orders) takes roughly 47 ms, which is comfortable.
- **The worst path** (the uncertain band triggers the vendor call) takes about 87 ms, leaving **13 ms of headroom**.
- The vendor call is by far the biggest piece. That's why the value-of-information cascade from 4.4 is a latency tool, not just a cost tool.
- Feature fetches run **in parallel**. Done one after another, they'd blow the budget alone.

### How latency reshapes the formulation

1. **Heavy features move to batch or streaming.** "Fraud rate among orders sharing this device over 90 days" is computed ahead of time, not per request. The cost is **staleness**, and a fraud ring can strike in minutes.
2. **Heavy tasks become features.** The graph model (4.1) can't run in 100 ms, so it runs nightly and its output becomes a checkout feature.
3. **Model size is capped.** A few hundred trees fit. A large sequence model may need to be distilled into a smaller one, or moved to an async decision.
4. **Split the decision.** When the budget really binds, make a **fast provisional decision now and a richer one later**: approve at checkout, then run the heavy model before shipping and hold the order if needed. This is 1.1's multi-decision-point design, forced by latency. The trade-off from the 1.1 timeline applies: acting later means more information and less preventable loss.
5. **Plan for timeouts.** What happens at 100 ms is a *policy decision*, not an engineering accident:

| Timeout default | Risk |
|---|---|
| Approve (fail-open) | Fraud gets through on slow days |
| Decline (fail-closed) | Revenue lost on slow days |
| **Rules fallback, step-up for high amounts** (ShopFast) | Some friction, bounded loss |

### Assumptions

- The budget is **real**. Negotiate it: sometimes 100 ms is inherited folklore and 150 ms is fine.
- Upstream services (feature store, vendor) **meet their p99 targets**, including at peak.
- **Traffic peaks are known**: Black Friday brings about 10× normal load.

### Design choices

1. **Serving mode per decision** (table above).
2. **Budget allocation**: how many ms go to features vs model vs vendor.
3. **Precompute vs compute per request**: freshness against latency.
4. **Timeout default action**: a cost-matrix question (1.4), decided ahead of time.
5. **Model size limit**: set it before the modeling team picks an architecture.

### Trade-offs

- **Freshness vs latency vs cost**: streaming counters are fresh and fast but need infrastructure (5.2). Batch is cheap but stale.
- **Model richness vs budget**: a bigger model is more accurate and slower, and tail latency grows with load.
- **Synchronous vs async**: acting at checkout prevents more loss with less information; pre-shipment has more information and prevents less.

### Failure modes

- **Thinking in averages.** p50 is 30 ms, but p99 on Black Friday is 140 ms. Eight percent of requests time out, the fallback handles them, and fraud spikes on your highest-volume day.
- **Silent fail-open.** A timeout returns "approve" by default because that's what the HTTP client did. Nobody decided it.
- **Adversarial slowness.** Fraudsters notice that huge carts or odd inputs slow scoring down past the timeout, and they exploit the fail-open path. Timeouts are an attack surface (6.4).
- **Stale batch features during an attack.** A ring strikes at 2 PM, and the nightly ring score catches it tomorrow.
- **Offline–online feature mismatch.** Training uses precise, fresh warehouse aggregates while serving uses cached or approximate ones. Skew (2.3) caused by latency shortcuts.
- **Retry storms.** Timeouts trigger retries, which double the load, which causes more timeouts.

### Connections

- **← 1.1**: the decision point sets the budget, and splitting decisions is the escape hatch.
- **← 2.3**: the serving path for each data source.
- **← 4.3**: event-triggered vs batch cadence.
- **← 4.4**: the cascade saves latency.
- **← 2.1**: the rules fallback is the timeout path.
- **→ 5.2**: streaming and serving infrastructure costs.
- **→ 6.4**: timeouts as an attack surface.
- **→ Stages 7–8**: serving infrastructure, p99 monitoring, load testing before peak season.

## 5.2 Scale and cost

### What problem it solves

Every prediction costs something: compute, data, vendor fees, labels, people. At scale, **cost per decision** has to stay well below **value at stake per decision**, or the system loses money no matter how accurate it is.

This is a framing question because it decides *which units get scored, how heavy each model can be, and where ML shouldn't run at all*.

### The key idea: scale differs by unit

Part 4.3 split ShopFast into units. Each unit has a very different volume, so each can afford a very different cost per item. "Fraud" isn't one scale problem; it's a funnel:

<Diagram src="problem-framing/volume-funnel-by-unit.svg" />

Reading the funnel:
- **Orders are only about 10M/yr**, roughly 0.3/sec on average and about 5/sec at peak. Serving the checkout model is **not** where the scale problem is.
- The real volume sits **upstream**: clickstream feeding streaming features, logins for the takeover model, and payment attempts, which spike during card-testing attacks.
- **Downstream, items are rare and expensive**: each review costs $3 of human time, and each chargeback is a label worth a lot.

### How it works: unit economics per decision

**The rule: cost per decision ≪ value at stake per decision.**

| Unit | Value at stake per item | Affordable cost per item | Implication |
|---|---|---|---|
| Order | ~$200 × 0.2% fraud ≈ **$0.40+** expected fraud, plus false-decline risk | Cents | Full model, vendor call in the uncertain band |
| Login | Takeover losses ~$1.5M ÷ 150M logins ≈ **$0.01** | Fractions of a cent | Light model; score fully only on risk triggers (new device, new geography) |
| Payment attempt | Tiny per attempt; bursts of thousands | ~$0 | Rate limits and rules. No ML per attempt, no paid calls. |
| Review | ~$25–200 of savings on flagged orders | $3 | Spend human time only on the top-savings orders (4.4) |

### Where the cost actually goes

A typical ML fraud system's run costs, from largest to smallest:
1. **People**: maintenance, retraining, on-call, investigations. Often the **largest** line, and the most forgotten one (2.4). Each extra model in the portfolio (4.1) adds a lasting fraction of a person.
2. **Streaming feature infrastructure**: continuous aggregates over billions of events.
3. **Human labeling**: reviews at $3 each. That's real money, *and* a label source.
4. **Third-party data**: vendor calls.
5. **Experimentation**: the fraud dollars lost to exploration and holdouts (3.4, 6.2).
6. **Serving and training compute**: usually *smaller* than people expect for tabular fraud models.
7. **Logging and storage**: a feature snapshot for every decision (4.4) is cheap for orders and expensive for clickstream.

### Framing choices driven by scale

1. **Match model weight to value per decision**: a heavy model on orders, a light one on logins, rules on payment attempts.
2. **Score on triggers, not everything**: a full takeover score only when a login shows a new device or location. That's roughly 10% of logins, so a 10× saving.
3. **Put cheap filters before paid calls**: rate limits and rules run *before* any vendor call or heavy feature.
4. **Size for peak, not average**: Black Friday brings about 10× load, and attacks bring spikes on top.
5. **Plan for growth**: design for 3–5× volume. Costs that grow in step with volume (vendor per call) behave very differently from roughly fixed ones (a model).
6. **Label budget as a design lever**: part of the review capacity can go to orders chosen for **label value** (where the model is most uncertain), not just immediate savings. This is where 6.2 picks up.

### Assumptions

- **Volume forecasts** hold, including attack spikes.
- **Unit prices** (vendor, compute, reviewer wages) stay stable, or have contract caps (2.4).
- **Value-at-stake estimates** per unit are right. Takeover losses might be underestimated because of silent fraud (4.2).

### Design choices

1. **Which units get ML, rules, or nothing.**
2. **Triggered vs exhaustive scoring** per unit.
3. **Retraining cadence**: monthly retraining on 2 years of data vs weekly incremental updates. Freshness against compute and people cost.
4. **Build vs buy infrastructure**: a managed feature store vs your own.
5. **How review time is split** between immediate savings and label value.

### Trade-offs

- **Coverage vs cost**: scoring every login catches more takeovers and may cost more than the takeovers do.
- **Freshness vs cost**: streaming everything is fresh and expensive; batch is cheap and stale (5.1).
- **Portfolio breadth vs team capacity**: seven specialized models cost more to maintain than three good ones. Maintenance is forever.

### Failure modes

- **Cost per decision above value**: a heavy takeover model on every login costs $1.2M/yr to prevent $1.5M in losses, and it only catches half of them.
- **Denial-of-wallet**: a card-testing attack sends 200k attempts an hour, and each one triggers a paid vendor call. **The attacker runs up your bill** even when every attempt fails. Cheap filters must come before paid calls.
- **Unbounded logging**: feature snapshots for clickstream-level events, with storage costs growing faster than traffic.
- **Sizing for the average**: autoscaling limits set for normal days, and Black Friday latency collapses (5.1).
- **Ignoring people cost**: the ROI (2.4) counted compute and forgot the three engineers keeping it alive.

### Connections

- **← 2.4**: run costs and ROI.
- **← 4.3**: units define the scale per unit.
- **← 4.4**: the cascade and value-of-information logic are cost tools too.
- **← 5.1**: freshness, latency and cost form a triangle.
- **→ 6.2**: review budget as a labeling and exploration budget.
- **→ 6.4**: denial-of-wallet and attack spikes.
- **→ Stage 7**: capacity planning, autoscaling, cost monitoring.

## 5.3 Explainability and regulation

### What problem it solves

A declined customer asks "why?" A regulator asks "how does this work?" A reviewer asks "what should I look at?" A card network asks "what's your evidence?"

If the system can't answer these, it can't legally or practically operate in many settings, however accurate it is. Like latency, these requirements **constrain the formulation**: which model classes, which features, which actions (a human appeal path), and what gets logged.

> Not legal advice. Regulation varies by country and changes over time. The job of framing is to **surface the questions early and bring Legal in** (1.2). Legal answers them.

### How it works

**Step 1: identify the regimes that may apply.** Examples to raise with Legal for ShopFast:
- **Automated decisions (e.g., EU GDPR, Article 22)**: rights around decisions based *solely* on automated processing with significant effects, including human intervention and the right to contest. Fraud prevention is often a recognized basis for such processing, but **safeguards and transparency still apply**.
- **Payment authentication rules (e.g., EU strong customer authentication)**: govern when step-up is required and when risk-based exemptions apply. This directly shapes the action space (1.1).
- **AI-specific rules (e.g., EU AI Act)**: at the time of writing, fraud detection is carved out of the "credit scoring" high-risk category. **But** the classification depends on the use.
- **Credit rules**: if ShopFast launches **buy-now-pay-later** and uses a risk model to approve it, that's a *credit* decision. Credit comes with its own explanation obligations (e.g., adverse-action notices in the US) and higher-risk treatment. **The same model, used for a different decision, falls under a different regime.**
- **Card-network dispute rules**: fighting a chargeback requires *evidence*, a form of explanation after the fact.

**Step 2: design explanations per audience.** Different audiences need different detail, and detail is also a **gaming risk** (3.2):

<Diagram src="problem-framing/explanation-tiers-by-audience.svg" />

**Step 3: choose explanation mechanics.**

| Kind | What it answers | Tools |
|---|---|---|
| **Global** | How does the model work overall? | Feature importance, partial dependence, model documentation ("model card") |
| **Local** | Why *this* decision? | Per-decision attributions (e.g., SHAP), mapped to **reason codes** |
| **Built-in** | The model is readable itself | Logistic regression / scorecards, GAMs, trees with **monotonic constraints** |
| **Counterfactual** | What would change the outcome? | "Approved if X were different." Useful internally, **dangerous for customers** (it's a gaming guide) |

**Reason codes** are the workhorse. Group raw feature attributions into about 15–30 stable, readable categories, such as "device linked to prior fraud," "unusual shipping pattern" or "velocity: many cards." Every decision logs its top 3 codes (4.4). Support staff, analysts and auditors all read from that one source.

**Monotonic constraints** are an underrated tool. For example: "more prior successful orders never *increases* risk." This makes the model's behavior defensible and resistant to strange extrapolation, usually at very little accuracy cost for tabular models.

**Step 4: design the human path.** Significant automated decisions need a way for a person to **contest them and get a human review**. For ShopFast:
- A declined customer can reach support.
- Support sees the reason codes and can **re-route to review or override**, within limits.
- Each override is logged, and becomes a label signal (with care, as with reviewer echo in 4.2).

That path uses review capacity (4.4, 5.2). Budget for it.

### Assumptions

- **Explanations are faithful** to what the model actually did. Post-hoc methods are approximations.
- **Legal's interpretation** of the regimes is current, and gets re-checked when the product changes (e.g., BNPL).
- **Reason-code categories stay stable** across model versions, so support scripts and audits don't break.

### Design choices

1. **Built-in vs post-hoc explanations.** For tabular fraud models, **gradient-boosted trees + monotonic constraints + SHAP-based reason codes** is a common middle path.
2. **Reason-code taxonomy**: its granularity and who owns it.
3. **Tier access**: which audience sees which detail (diagram).
4. **When to compute explanations.** Computing SHAP inline costs latency (5.1). Compute it **asynchronously, and only for declines, step-ups and reviews**. Approvals rarely need an explanation in the moment.
5. **Documentation package**: model card, data lineage, validation results, monitoring plan, change log. Build it as you go, not the week before an audit.

### Trade-offs

- **Accuracy vs interpretability**: often a smaller gap than people expect for tabular data. Large when the signal lives in complex sequences or graphs.
- **Transparency vs gaming**: every detail you tell customers teaches attackers (3.2). The answer is tiering: coarse for the public, detailed behind access control.
- **Human appeal vs cost**: a real appeal path takes reviewer hours; a fake one creates regulatory and reputational exposure.
- **Explanation fidelity vs simplicity**: an accurate attribution across 200 correlated features doesn't read well; a simple reason code simplifies.

### Failure modes

- **Unfaithful explanations**: correlated features share or swap credit. The reason says "new account" while the real driver was a linked device. The reviewer investigates the wrong thing.
- **Gaming leak**: customer messages or counterfactuals ("approved if your account were 7+ days old") teach fraudsters exactly what to fake.
- **Sensitive reasons**: "declined because of your postal code area" can reveal a proxy for a protected attribute, which is a fairness and legal problem (5.4).
- **Dead-end appeals**: support can't see reasons or can't override, so good customers are stuck and complaints escalate to regulators or social media.
- **Version mismatch**: the explanation is generated by a different model version than the one that decided, because the version wasn't logged (4.4).
- **Scope creep across regimes**: the fraud model is reused for BNPL approvals without re-framing, and a credit regime now applies that nobody prepared for.

### Connections

- **← 1.2**: Legal and compliance as stakeholders with veto power.
- **← 2.1**: deterministic hard rules for legally mandated checks.
- **← 3.2**: explainability vs gaming.
- **← 4.4**: reason codes and complete decision logs.
- **← 5.1 / 5.2**: explanation latency and review capacity.
- **→ 5.4**: fairness. Explanations reveal proxies.
- **→ Stages 7–8**: model documentation, audit logs, monitoring the reason-code distribution.

## 5.4 Fairness and privacy

### What problem it solves

Fraud models make two kinds of harm that fall **unevenly**:
- **Unfair burden**: false declines and step-ups concentrated on certain groups, e.g., customers from certain countries, people on cheap Android phones, non-native-language users, or people living in certain postal codes.
- **Privacy intrusion**: fraud detection wants *as much data as possible* (devices, locations, linked identities, behavior), while privacy law and user trust push for *as little as necessary*.

Both create legal exposure, reputational damage and lost customers. Both change the formulation: features, labels, thresholds and data handling.

Same caveat as 5.3: **raise these questions with Legal. This isn't legal advice.**

### The three-way tension

Fraud detection, privacy and fairness pull against each other in pairs:

<Diagram src="problem-framing/privacy-fairness-tensions.svg" />

- **Fraud vs privacy**: fraudsters use VPNs, private-relay emails and cookie blocking. So do privacy-conscious legitimate customers. Features like "uses VPN" have real lift *and* penalize people for protecting their privacy. That's a fairness problem too.
- **Fraud vs fairness**: the model never sees protected attributes, but **proxies** carry them: postal code, name and email patterns, language, device price, prepaid cards (more common among lower-income customers), IP geolocation. Declines concentrate without anyone intending it.
- **Privacy vs fairness**: to *check* whether declines fall unevenly on protected groups, you often need data on group membership, which privacy rules restrict you from collecting or inferring.

### How it works: fairness

**1. Pick the harm, then the metric.** At checkout, the harm to good customers is a **false decline or unnecessary step-up**. The most meaningful metric is:

> **False-decline rate among legitimate customers, per group**, plus **calibration per group** (so the cost policy is equally correct for everyone).

Not the raw decline rate. If fraud *attacks* genuinely target some segments more, raw decline rates will differ even under a fair model.

**2. Know the impossibility result.** When base rates differ between groups, a model **cannot** be calibrated within every group *and* have equal false-positive and false-negative rates across groups at the same time (except in trivial cases). You must **choose** which property to protect. That's a values decision owned by stakeholders and Legal (1.2), not a hyperparameter.

**3. Audit segments.** Country, language, device tier, new vs returning, payment type, plus protected attributes *where it's lawful and feasible to measure them*. Look at **combinations** too, e.g., new customer + prepaid card + non-English locale.

**4. Mitigations, roughly in order of preference:**
- **Better signal for underserved groups**: thin-history customers need other trustworthy signals, not harsher thresholds.
- **Softer actions**: step-up instead of decline where the model is uncertain for a segment (1.4 action space).
- **Proxy review**: examine high-lift features that track group membership (VPN, postal code, device tier). Removing one isn't a cure, since correlated features take over, but it's part of the review.
- **Segment guardrails**: the "≤ 2× baseline decline ratio" from 1.3, with its shadow price made visible (3.3).
- **Group-specific thresholds**: legally sensitive in some jurisdictions. Only with Legal's approval.

**5. Watch the label trap.** Over-declined groups get **fewer labels** (declined orders are unknown, 4.2). So the model stays uncertain about them and keeps declining them. Unfairness can reinforce itself (6.2, 6.3). **Exploration** is also a fairness tool: it measures false declines where you're otherwise blind.

### How it works: privacy

1. **A lawful basis per data source**: extend the 2.3 inventory with purpose, basis, retention and who else receives the data.
2. **Minimize**: use derived features instead of raw data (hashed emails, tokenized device IDs, aggregates instead of raw location trails).
3. **Pseudonymize the logs**: decision logs (4.4) are a goldmine of personal data. Restrict access, encrypt, and audit who reads them.
4. **Plan retention**: labels need 120 days to mature (4.2), plus training history. Define how long each piece is kept, and why.
5. **Plan for deletion requests**: when a customer asks to be deleted, what happens to their rows in training data and in fraud records? Fraud prevention may justify keeping some data in some regimes, **but decide this with Legal before launch**.
6. **Vendor data sharing**: the device-fingerprint vendor sees your customers' data. It needs a data-processing agreement, and possibly a cross-border transfer review.

### Assumptions

- Groups can be **identified well enough** to audit, lawfully.
- Stakeholders **agree on the fairness definition**.
- Legal's view of the lawful basis and retention **matches how the data is actually used**.

### Design choices

1. **Fairness metric**: false-decline parity among legitimate customers vs calibration per group vs something else. You can't have all of them.
2. **Audit segments and cadence**: every model version, plus monthly in production.
3. **Mitigation mix**: better features, softer actions, guardrails, thresholds.
4. **Privacy posture**: collect broadly and protect heavily vs minimize at the source.
5. **Measuring protected attributes**: don't measure (blind), infer statistically (risky), or collect with consent for auditing (costly and sensitive).

### Trade-offs

- **Fairness constraints cost TCF**: the shadow price (3.3) makes the cost visible. Whether to pay it is partly a *values and legal* decision, not only an economic one.
- **Minimization vs signal**: less data means less lift. Some high-lift features aren't worth their privacy cost.
- **Retention for labels vs deletion rights**.
- **Auditability vs privacy**: fairness checks need exactly the attributes privacy protects.

### Failure modes

- **"Fairness through unawareness"**: "we don't use race or nationality, so we're fair." Proxies carry them anyway.
- **Measuring the wrong rate**: comparing raw decline rates (misleading when attack rates differ) instead of false declines among legitimate customers.
- **Missing intersections**: every single segment passes, and one combination is declined 6× more.
- **Penalizing privacy**: VPN and private-email users become second-class customers.
- **Self-reinforcing exclusion**: the label trap above, never broken without exploration.
- **Personal-data leak from logs**: decision logs copied into analytics tools without access controls.
- **Vendor without data-processing terms**: customer data shared with no contractual protections.
- **Deletion breaks reproducibility**: a deletion request removes training rows, and the old model can no longer be rebuilt for an audit. Version datasets with deletion handling in mind.

### Connections

- **← 1.2**: Legal and affected customers as stakeholders; decision rights over the fairness definition.
- **← 1.3 / 3.3**: segment guardrails and shadow prices.
- **← 1.4**: softer actions as mitigation.
- **← 2.3**: the data inventory gains lawful basis and retention columns.
- **← 5.3**: sensitive reason codes reveal proxies.
- **→ 6.2 / 6.3**: label starvation and self-reinforcing loops.
- **→ Stage 8**: per-segment monitoring in production.
